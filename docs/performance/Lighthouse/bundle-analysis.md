# JavaScript Bundle Analysis

## Context

This document analyzes the JavaScript bundles generated by the Angular production build of Personal Expense Manager.

The analysis is based on:

- Lighthouse performance baseline
- Angular CLI `stats.json`
- Production build
- `/expenses` route

The purpose is to identify the sources of the JavaScript payload and determine which parts are candidates for optimization.

## Lighthouse Baseline

Lighthouse reported:

- Performance: 94
- Estimated unused JavaScript: 83 KiB
- Estimated savings: 84,722 bytes
- JavaScript execution time: 268.988 ms
- Main-thread work: 678.524 ms
- JavaScript transfer size: 194,807 bytes

These values represent the baseline before bundle optimization.

## Bundle Overview

### `chunk-33MHLDIH.js`

- Size: 263,004 bytes
- Entry point: `ExpensesPage`
- Represents the `/expenses` feature.

The largest contributors are:

| Dependency                            | Bytes in output |
| ------------------------------------- | --------------: |
| `@angular/material/form-field2.mjs`   |          54,838 |
| `@angular/cdk/overlay-module.mjs`     |          40,863 |
| `@angular/cdk/table.mjs`              |          26,939 |
| `@angular/material/button.mjs`        |          25,430 |
| `@angular/material/select-module.mjs` |          25,021 |
| `@angular/material/dialog-module.mjs` |          16,096 |

This indicates that a significant part of the feature chunk comes from Angular Material and CDK functionality used by the expenses page.

## `chunk-WAGTDBVM.js`

- Size: 212,885 bytes
- No direct imports
- Contains shared Angular/RxJS/framework code.

One particularly large contributor is:

`@angular/core/fesm2022/debug_node.mjs` — 97,745 bytes.

This is framework-level code rather than application-specific code and should not automatically be treated as removable application code.

Other notable contributors include Angular signals/effects/runtime and RxJS modules.

## Resource Size vs Transfer Size

The bundle analysis must distinguish between:

- resource size
- compressed transfer size
- JavaScript actually executed
- JavaScript classified as unused by Lighthouse

For example:

| Chunk               | Resource size | Transfer size |
| ------------------- | ------------: | ------------: |
| `chunk-33MHLDIH.js` |       ~263 KB |        ~58 KB |
| `chunk-WAGTDBVM.js` |       ~213 KB |        ~71 KB |

Therefore, reducing the uncompressed bundle size does not necessarily produce the same reduction in network transfer or page-load time.

## Initial Findings

### Finding 1 — Material/CDK contributes significantly to `/expenses`

The `ExpensesPage` chunk contains substantial Angular Material/CDK code, including table, dialog, form-field, select and overlay functionality.

This is expected to some degree because these features are used by the page, but the exact loading boundary should be investigated.

### Finding 2 — Lighthouse unused JavaScript is not equivalent to dead application code

The Lighthouse estimate of 84,722 bytes should not be interpreted as 84 KB of code that can simply be deleted.

Unused code can result from:

- code loaded before it is needed
- shared dependencies
- feature dependencies
- framework/runtime code
- code required after user interaction

Further analysis is required before making optimization changes.

### Finding 3 — `debug_node` requires separate consideration

`debug_node.mjs` accounts for approximately 97.7 KB of the generated resource contribution.

This is Angular framework code and therefore should be investigated separately from application-level optimization opportunities.

It should not be removed manually from `node_modules` or excluded through an unsafe build hack.

## Optimization Hypotheses

### Hypothesis A — Lazy-load dialog/form functionality

The `/expenses` feature contains both the expense table and functionality related to creating expenses.

If the create-expense dialog and its form are loaded as part of the initial `/expenses` chunk, this may represent an opportunity for additional code splitting.

A potential optimization would be to load dialog/form-related dependencies only when the user opens the create-expense flow.

This hypothesis must be validated against the actual dependency graph before implementation.

### Hypothesis B — Investigate Material/CDK dependency boundaries

Determine whether all Material/CDK functionality included in `chunk-33MHLDIH.js` is required during the initial rendering of `/expenses`.

Do not optimize individual imports blindly. The goal is to determine whether functionality can be moved to a later loading boundary.

### Hypothesis C — Separate framework-level payload from application-level payload

The framework/runtime chunk should be analyzed separately from feature-specific application code.

The goal is to distinguish:

- Angular framework cost
- RxJS/runtime cost
- Angular Material/CDK cost
- application code cost

before deciding where optimization effort is worthwhile.

## Next Investigation

Before changing the application, generate a more detailed dependency analysis for the production build.

The next step is to identify the top contributors for each generated chunk and map them back to application features and user interactions.

No implementation changes should be made until the dependency graph confirms a concrete optimization opportunity.

## Baseline Conclusion

The current `/expenses` production build is relatively small in transferred size and achieves a Lighthouse Performance score of 94.

The largest reported optimization opportunity is JavaScript usage, with approximately 83 KiB of estimated unused JavaScript.

The current analysis suggests that the most promising application-level area to investigate is the loading boundary between the initial expenses page and secondary functionality such as the create-expense dialog.

Further optimization should be driven by bundle evidence rather than by Lighthouse savings alone.

## Optimization Experiment #1 — Lazy Loading Create Expense Dialog

### Change

The `CreateExpenseDialogComponent` was previously statically imported by `ExpensesPage`.

The static import caused the dialog, expense form and their Angular Material/CDK dependencies to be included in the `ExpensesPage` feature chunk.

The import was changed to a dynamic `import()` executed only when the user opens the create-expense dialog.

### Bundle Analysis — Before

The `ExpensesPage` entry point was included in:

| Chunk               |          Size |
| ------------------- | ------------: |
| `chunk-33MHLDIH.js` | 263,004 bytes |

The chunk contained both the page and dialog-related code, including:

- `CreateExpenseDialogComponent`
- `ExpenseFormComponent`
- Angular Material Dialog
- Angular Material Form Field
- Angular Material Select
- Angular Material Input
- Angular Material Button
- Angular CDK Overlay

### Bundle Analysis — After

After introducing the dynamic import, the `ExpensesPage` entry point moved to:

| Chunk               |         Size |
| ------------------- | -----------: |
| `chunk-CW3IFV3E.js` | 53,312 bytes |

The dialog became a separate dynamically loaded chunk:

| Chunk               |          Size |
| ------------------- | ------------: |
| `chunk-UYQKTJEZ.js` | 137,506 bytes |

The generated bundle graph explicitly marks the dialog as a `dynamic-import`.

### Result

The `ExpensesPage` chunk decreased from:

**263,004 bytes → 53,312 bytes**

Difference:

**209,692 bytes (~79.7% reduction)**

This does **not** mean that 209,692 bytes of JavaScript were removed from the application. Most of the dialog-related code was moved to a separate lazy-loaded chunk and is now deferred until the dialog is required.

### Interpretation

This optimization changes the loading boundary rather than removing functionality.

Before:

`/expenses` → ExpensesPage + Create Expense Dialog + Expense Form

After:

`/expenses` → ExpensesPage

`Create Expense` interaction → dynamically load dialog chunk

The expected benefit is a smaller initial feature payload and reduced JavaScript required during the initial `/expenses` navigation.

The actual user-perceived performance impact still needs to be validated with a second Lighthouse measurement.

### Validation

The next step is to verify the runtime behavior in Chrome DevTools Network:

1. Load `/expenses`.
2. Confirm that the lazy dialog chunk is not requested during initial navigation.
3. Open the Create Expense dialog.
4. Confirm that the dialog chunk is requested at that point.

A second Lighthouse run will then be used to compare the baseline against the optimized build.

**#### Lighthouse — After**

A Lighthouse audit was performed against the optimized production build.

| Metric                      |  Before |       After |
| --------------------------- | ------: | ----------: |
| Performance                 |      94 |      **94** |
| First Contentful Paint      |  2.27 s |  **2.41 s** |
| Largest Contentful Paint    |  2.68 s |  **2.52 s** |
| Total Blocking Time         | 13.5 ms |   **~1 ms** |
| Cumulative Layout Shift     |       0 |       **0** |
| Estimated unused JavaScript | ~83 KiB |  **60 KiB** |
| Total page payload          |       — | **221 KiB** |

The AFTER report records FCP at 2,413 ms and LCP at 2,521 ms.

TBT was measured at 1 ms and displayed by Lighthouse as `0 ms`; CLS remained exactly `0`.

Lighthouse estimated 60 KiB of potential unused JavaScript after the change.

The total network payload recorded by the audit was 226,200 bytes (221 KiB).

**#### Interpretation**

This optimization changes the loading boundary rather than removing functionality.

Before:

`/expenses` → ExpensesPage + Create Expense Dialog + Expense Form

After:

`/expenses` → ExpensesPage

`Create Expense` interaction → dynamically load dialog chunk

The bundle-level result clearly confirms that the initial `ExpensesPage` chunk became substantially smaller.

The Lighthouse result is more nuanced. The Performance score remained at 94, while LCP and TBT were slightly better in this particular run and FCP was slightly worse.

Because Lighthouse measurements have run-to-run variability, the single BEFORE/AFTER measurement is **not sufficient to attribute those metric changes directly to the lazy-loading change**.

**#### Network Evidence**

The AFTER Lighthouse report shows the initial navigation loading the main application chunks, including:

- `chunk-WNL7VUUF.js` — 70.6 KB transfer
- `main-QF4JBOVA.js` — 33.8 KB transfer
- `polyfills-5CFQRCPP.js` — 13.3 KB transfer

The dynamically loaded dialog chunk was not part of the initial navigation requests.

**#### Current Conclusion**

The optimization is confirmed at the **bundle and runtime loading-boundary level**:

- the `ExpensesPage` chunk was reduced by ~79.7%
- dialog code was moved into a separate lazy chunk
- the lazy chunk is deferred until the dialog is opened

The impact on real initial-load performance remains to be quantified statistically.

**#### Next Step**

Run several additional Lighthouse audits against the optimized build using exactly the same configuration.

The results will be compared using the median values rather than relying on a single run.

This will allow us to determine whether the observed LCP/TBT changes are reproducible and whether the optimization produces a measurable improvement in initial navigation performance.

**#### Repeated Lighthouse Measurements**

Four Lighthouse runs were performed against the optimized production build using the same configuration.

| Run | Performance |   FCP |   LCP |   TBT | CLS | Speed Index | Unused JS |

| #1  |          94 | 2.4 s | 2.5 s |  0 ms |   0 |       2.4 s |    60 KiB |
| #2  |          94 | 2.4 s | 2.6 s | 10 ms |   0 |       2.4 s |    60 KiB |
| #3  |          94 | 2.4 s | 2.5 s |  0 ms |   0 |       2.4 s |    60 KiB |
| #4  |          94 | 2.4 s | 2.5 s |  0 ms |   0 |       2.4 s |    60 KiB |

Median result:

- Performance: **94**
- FCP: **2.4 s**
- LCP: **2.5 s**
- TBT: **0 ms**
- CLS: **0**
- Speed Index: **2.4 s**
- Estimated unused JavaScript: **60 KiB**

The repeated measurements show that the optimized build produces highly consistent Lighthouse results. The Performance score remained at 94 across all four runs.

Compared with the original baseline, the median LCP improved from 2.68 s to 2.5 s, while estimated unused JavaScript decreased from approximately 83 KiB to 60 KiB.

However, the Lighthouse score itself did not increase. The observed metric differences should therefore not be attributed exclusively to the lazy-loading change. The strongest evidence of the optimization remains the bundle-size reduction and the verified runtime loading boundary.

# AI-Assisted Feature Review — Budgets

## Overview

The `Budgets` feature was developed as an AI-assisted implementation experiment.

A large part of the initial feature implementation was generated by AI, including the Angular components, state management, API layer, dialog flow and initial test suite. The generated code provided a strong starting point and was generally aligned with the existing architecture of the project.

However, the initial implementation was not treated as production-ready code. It went through several rounds of manual review, refactoring, testing and debugging.

The main conclusion from the experiment is:

> AI was highly effective at generating the structure and repetitive implementation of the feature, but human engineering judgment was still required to validate architectural decisions, identify subtle framework-specific issues and turn generated tests into meaningful behavioral coverage.

---

## Feature Scope

The generated `Budgets` feature included:

- lazy-loaded `Budgets` route
- `BudgetsPage`
- `BudgetsPageStore`
- `BudgetsStore`
- `BudgetsApiService`
- budget DTO and domain models
- DTO-to-domain mapping
- create / edit / delete flows
- Angular Material dialog integration
- reactive budget form
- custom amount validation
- loading and error states
- monthly budget filtering
- budget vs. expense calculations
- category-based budget rows
- Angular Signals and NgRx Signal Store
- unit and component tests

The generated implementation therefore covered most of the expected feature surface rather than only individual UI elements.

# What AI Did Well

## 1. It quickly produced a complete feature skeleton

The biggest advantage was speed.

Instead of implementing every layer manually, AI was able to generate a complete first version spanning:

```text
Route
  ↓
Page
  ↓
Page Store
  ↓
Domain Store
  ↓
API
  ↓
DTO mapping
```

This gave a usable starting point for the feature very quickly.

For repetitive Angular code, such as CRUD methods, dialog wiring, form controls and template structures, AI was particularly effective.

---

## 2. The implementation generally followed the existing architecture

The generated feature was not completely isolated from the rest of the application.

It adopted the project's existing architectural patterns:

- feature-first organization
- standalone Angular components
- Signals
- NgRx Signal Store
- feature-level state
- Angular Material
- lazy routing
- DTO/domain separation

The `BudgetsPage` remained relatively thin and delegated state and business operations to `BudgetsPageStore`.

This was important because the goal was not merely to make the feature work, but to make it fit the architecture of the existing application.

---

## 3. AI was strong at established Angular patterns

Several implementation patterns were produced correctly with relatively little manual intervention.

Examples included:

```text
inject()
Signals
rxMethod()
tapResponse()
@if / @else
@for
standalone components
feature-scoped providers
MatDialog
Reactive Forms
```

These are patterns with relatively well-defined implementation shapes, which makes them particularly suitable for AI-assisted development.

---

## 4. The create/edit dialog flow was implemented effectively

The generated dialog architecture was eventually kept deliberately thin:

```text
BudgetForm
    ↓ save
BudgetDialog
    ↓ close(result)
BudgetsPage
    ↓
BudgetsPageStore
```

The dialog was not turned into another state-management layer.

This was a good architectural result and demonstrated that AI can correctly reproduce an established component-boundary pattern when the intended responsibilities are sufficiently clear.

# Where Human Intervention Was Required

## 1. Architectural review was more important than code generation

The first generated implementation was not accepted as-is.

The initial review identified several issues that were not obvious from simply looking at whether the code compiled:

- responsibilities were not always separated cleanly
- some state calculations were duplicated
- the relationship between page state and domain state required refinement
- some API behavior was unnecessarily simulated
- tests did not provide enough behavioral coverage
- some generated abstractions were more complicated than necessary

The architecture therefore evolved through review rather than being accepted from the initial generation.

One important example was the `BudgetsPageStore`.

The final version separates:

```text
raw feature state
    ↓
current-month data
    ↓
aggregated values
    ↓
view-model rows
```

For example:

```text
currentMonthBudgets
currentMonthExpenses
        ↓
totalBudget
totalSpent
isEmpty
categoryBudgetRows
        ↓
remainingTotal
percentUsed
```

This structure was deliberately reviewed and refactored manually.

---

## 2. The initial tests were much weaker than the production code

This was one of the clearest differences between AI-generated code and the manually reviewed result.

The initial tests often checked that a method existed or that a spy was called, but did not sufficiently verify:

- state transitions
- error handling
- derived state
- replacement/removal semantics
- realistic asynchronous behavior
- actual rendering conditions
- create vs. update behavior
- component/store boundaries

The tests therefore required a significant amount of manual expansion.

The result was a much more comprehensive test suite covering the actual behavior of:

```text
BudgetsStore
BudgetsPageStore
BudgetFormComponent
BudgetsPage
```

rather than merely checking that individual methods could be invoked.

# Important Debugging Findings

## 1. Angular dependency injection required human debugging

One of the most interesting problems appeared in the `BudgetsPage` tests.

A `MatDialog` mock was registered:

```ts
{
  provide: MatDialog,
  useValue: dialogMock,
}
```

A direct TestBed check confirmed that the test injector contained the mock:

```ts
expect(TestBed.inject(MatDialog).open).toBe(dialogMock.open);
```

However, clicking the button still resulted in the real Material Dialog implementation being invoked.

This produced:

```text
_MatDialog.open
TypeError: Cannot read properties of undefined (reading 'push')
```

The important point was that:

> The fact that `TestBed.inject(MatDialog)` returns the mock does not automatically prove that the component under test resolves the same instance.

The issue required understanding Angular's provider hierarchy and the component-level injector created by the standalone component.

The test setup ultimately had to explicitly override the component's `BudgetsPageStore` provider and carefully control the dependencies available to the component.

This was not something that could be reliably solved by simply generating more mock code.

### Engineering lesson

AI can generate a syntactically correct dependency mock while still missing the framework-level dependency-resolution behavior that determines whether the mock is actually used by the component.

This is a good example of where framework knowledge is more valuable than code generation speed.

---

## 2. Rendering conditions had to be understood, not guessed

Another example appeared in the `BudgetsPage` component tests.

A test created:

```ts
categoryBudgetRows = [row];
```

but the Edit button was still not rendered.

The reason was in the template:

```text
@if (isEmpty()) {
    empty state
} @else {
    budget rows
}
```

The test had created data for the `@for` block, but had not satisfied the condition required to reach that block.

Therefore:

```text
categoryBudgetRows = [row]
        ↓
isEmpty() === true
        ↓
empty state rendered
        ↓
@for not executed
        ↓
Edit button does not exist
```

The test had to prepare the state required to reach the intended rendering path.

### Engineering lesson

A component test is not simply:

> "Set the data I want and click the button."

It is:

> "Prepare the minimum state required for the component to reach the behavior I want to test."

This distinction became important while debugging the generated tests.

---

## 3. Test mocks can accidentally represent impossible states

During the debugging process another subtle issue emerged.

In the production store, `isEmpty` is derived from the budget data.

In a simplistic mock, however, it is possible to create an inconsistent state such as:

```text
categoryBudgetRows = [row]
isEmpty = true
```

The real store would never produce that combination.

This raised an important testing question:

> Should the test explicitly set every derived value, or should the mock reproduce the dependency between those values?

For isolated component tests, explicitly controlling the state is acceptable when the objective is to test the component's behavior for a given store state.

However, mocks should ideally avoid creating unrealistic combinations of values when those combinations can never occur in production.

### Engineering lesson

A mock is not automatically "good" simply because it is easy to configure.

A good mock should expose the contract required by the component while avoiding unnecessary duplication of production logic.

# What Required the Most Human Reasoning?

The most valuable manual work was not writing the most lines of code.

It was answering questions such as:

```text
Should this logic live in the component or the store?

Is this computed signal actually necessary?

Does this test verify behavior or only implementation?

Is the mocked state something that can exist in production?

Why is the button missing from the DOM?

Why is the real MatDialog being called?

Is this async test checking the correct point in time?

Should this behavior be tested at page level or store level?
```

These questions required understanding the system rather than simply producing code.

---

# What AI Was Best At

AI was most effective when the problem had a recognizable implementation pattern:

```text
"Create a Signal Store with CRUD methods"
"Create a reactive form"
"Create a dialog wrapper"
"Create DTO mappings"
"Create Angular Material UI"
"Create unit-test scaffolding"
```

These tasks benefited heavily from AI assistance because they involve a lot of predictable code.

---

# What AI Was Least Reliable At

AI was less reliable when the task depended on understanding the exact runtime behavior of the application:

```text
Angular dependency injection hierarchy
component injector behavior
rendering prerequisites
derived state relationships
test isolation boundaries
asynchronous state transitions
realistic mock state
```

These areas required investigation rather than generation.

---

# The Development Process

The actual process was closer to:

```text
AI generates initial implementation
          ↓
Human reviews architecture
          ↓
AI fixes identified issues
          ↓
Human reviews again
          ↓
Tests expose hidden problems
          ↓
Human diagnoses framework behavior
          ↓
Tests are refined
          ↓
Feature is manually verified
```

This is materially different from:

```text
AI generates feature
        ↓
merge
```

The AI was effectively used as a **high-speed implementation assistant**, while the developer remained responsible for architecture and correctness.

---

# Overall Assessment

The experiment demonstrated that AI can significantly reduce the amount of manual work required to implement a medium-sized Angular feature.

The generated implementation was good enough to provide a strong foundation and covered a large amount of repetitive code.

However, the first generated version was not equivalent to a production-ready implementation.

The largest gap was not syntax or boilerplate. It was **engineering context**.

AI could generate:

```text
components
stores
services
forms
dialogs
tests
```

but the developer still had to determine:

```text
whether the boundaries were correct
whether the state model was sound
whether tests were meaningful
whether mocks were realistic
why framework behavior differed from expectations
and whether the final implementation actually matched the application's architecture
```

---

# Conclusion

The `Budgets` feature should therefore be considered an **AI-assisted implementation**, not simply an **AI-generated feature**.

AI provided substantial acceleration in implementation and was particularly effective for predictable Angular patterns and repetitive code.

The human contribution remained critical in:

- architectural decisions
- code review
- refactoring
- test design
- debugging
- framework-specific reasoning
- validating business behavior
- final quality assessment

The most important takeaway from the experiment is:

> **AI can significantly accelerate implementation, but it does not remove the need for engineering judgment.**

In this project, the value of the developer shifted away from writing every line manually and toward **reviewing, reasoning, validating and correcting the implementation produced by AI**.

That makes the experiment less about "Can AI build an Angular feature?" and more about:

> **"How effectively can an experienced developer use AI to accelerate feature development while retaining control over architecture and quality?"**

For this feature, the answer was: **very effectively — provided that the generated implementation was treated as a draft rather than as the final result.**
